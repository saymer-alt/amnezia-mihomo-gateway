# Участие в проекте / Contributing

Предложения, исправления опечаток, проверенные технические замечания и небольшие Pull Requests приветствуются.

## Перед созданием Issue или PR

1. Прочитайте [README](README.md) и документацию проекта.
2. Проверьте существующие Issues и PR на дубли.
3. Для ошибок используйте форму Bug report; для улучшений — Feature request.
4. Работайте в отдельной ветке от актуального `main`; присылайте минимальный diff и объясняйте проверку.

## Особенности проекта

- Прочитайте `AGENTS.md`, `README.md` и документацию об installer/rollback до изменения логики.
- Для сетевых ошибок указывайте Debian/Ubuntu, версии Docker/AmneziaWG/Mihomo и симптомы, но не раскрывайте IP VPS, ключи или конфигурации клиентов.
- Изменения маршрутизации, sysctl, watchdog и fail-secure требуют объяснения рисков, безопасного rollback и подтверждённых проверок.
- Различайте ветку `main` (разработка) и `stable` (установка); не предлагайте непроверенные команды для production VPS.

## Проверки и описание изменений

- Опишите наблюдаемое и ожидаемое поведение, точные версии и ограничения.
- Приведите минимальный пример или ссылку на источник; удалите из логов и примеров закрытые данные.
- Запустите применимые проверки из `tests/` и CI, либо явно укажите, что не удалось проверить.
- Не заявляйте тестирование на физическом оборудовании/production VPS, если теста не было.
- Не изменяйте теги релизов или `stable` в обычном PR к документации.

## Конфиденциальность

Нераскрытые уязвимости и секреты **не** публикуйте через публичные Issues/PR. Приватный канал раскрытия уязвимостей должен быть настроен и проверен отдельно. Публичные Issues предназначены только для несекретных ошибок.

## Стандарт небольших и проверяемых изменений

Для всех проектов `saymer-alt` действует [общий инженерный стандарт ревью](https://github.com/saymer-alt/saymer-infrastructure/blob/main/docs/engineering-change-review-standard.md). Это правило для **людей и ИИ**, а не файл инструкций агенту.

**Одна проблема → минимальное смысловое исправление → необходимые тесты → один обозримый PR → подтверждение результата.** Не смешивайте hotfix с рефакторингом, переименованиями и посторонними функциями. Если найден другой независимый дефект — отдельное Issue/PR. Размер изменений определяется не количеством строк, а возможностью доказать и проверить их; не отрывайте обязательные тесты и миграции от исправления. Большой неделимый diff требует отдельного обоснования и review. В описании PR указывайте границы, проверки и `NOT_TESTED`; CI PASS не означает field/runtime PASS. Проектные правила безопасности, веток и выпуска сохраняются.
